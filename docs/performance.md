# Replication performance

Measured end to end: the connector runs as a subprocess, exactly as the Airbyte
platform runs it, and RECORD messages are counted against wall-clock time. The
figures therefore include the SAP round trips, DuckDB, the CDK's serialization
and the write to stdout — not just the extraction.

Generated by `bin/benchmark.py`, which refuses to run while anything else is
talking to the same SAP system.

## The headline: project your columns

| Case | Records | Time | Records/s |
|---|---:|---:|---:|
| `DD02L`, all 55 columns, serial | 164,673 | 17.4s | 9,450 |
| `DD02L`, 2 of 55 columns, serial | 164,673 | 5.7s | **28,707** |

Restricting **Columns** pushes the projection into SAP and is worth **3x** on a
wide table. It is the single most effective setting this connector exposes, and
it costs nothing but naming the fields you actually want.

## Partitioning helps narrow extracts and hurts wide ones

This one is counter-intuitive and worth stating carefully, because the ERPL
extension's own published benchmark reports a 2.7x *speed-up* at eight
partitions. Both numbers are right; they measure different workloads.

Measured in raw DuckDB with no connector involved, on the same 164,673-row
table, varying only how many columns are actually fetched:

| Columns fetched | Serial | 8 partitions | Effect |
|---:|---:|---:|---|
| 1 of 55 | 2.1s (80,078/s) | 0.5s (345,522/s) | **4.3x faster** |
| all 55 | 19.3s (8,515/s) | 55.9s (2,945/s) | **2.9x slower** |

The sign flips with the width of the row. ERPL's benchmark is a single-column
extract, which is the regime where partitioning pays; a connector reading whole
rows is in the regime where it does not.

Through the connector, reading all columns, the penalty compounds:

| Partitions | Records/s |
|---:|---:|
| 0 (serial) | 9,450 |
| 2 | 1,152 |
| 4 | 776 |
| 8 | 508 |
| 16 | 516 |

**So `partitions` defaults to 0.** Raise it only together with a narrow
`columns` list, and measure on your own system before trusting it.

## Other protocols

| Case | Records | Time | Records/s |
|---|---:|---:|---:|
| `SBOOK`, wider transactional rows | 28,782 | 15.7s | 1,833 |
| ODP full, 1 thread | 3,001 | 1.9s | 1,575 |
| ODP full, 4 threads | 3,001 | 1.8s | 1,662 |
| ODP full, 8 threads | 3,001 | 1.9s | 1,579 |
| ODP over OData, initial load | 3,001 | 2.7s | 1,104 |

The ODP source here is too small for thread scaling to show; treat those three
rows as evidence that the threads setting is harmless at this size, not as a
scaling curve.

## How much does the connector itself cost?

Very little. Raw DuckDB reads all 55 columns of `DD02L` at 8,515 rows/s; the
connector, which additionally converts every row to JSON, constructs protocol
messages and writes them to stdout, manages 9,450 rows/s on the same data. SAP
dominates, and tuning effort belongs on the SAP side of the boundary —
projection, filters, and picking the right protocol.

## Reproducing

```bash
./bin/benchmark.py --list
./bin/benchmark.py --repeat 3 --markdown ../docs/performance.md
```

## Environment

- Host: Linux 6.18, 32 CPUs, 125 GB RAM
- Python 3.13, DuckDB 1.5.5, erpl v2026.09.04
- SAP: ABAP Platform Trial in a container on the same host

The SAP system shares a laptop with the connector, so these are *relative*
figures for comparing settings, not a capacity statement about production
hardware. Timings are reported, never asserted in tests: a threshold on a number
that moves with someone else's background job is a test that fails for reasons
nobody can act on.
